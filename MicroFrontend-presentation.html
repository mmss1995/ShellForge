The problem

Frontend monoliths don't scale with teams

01

Coupled deploys

One small fix waits for every team's release train.

02

Dependency conflicts

Everyone shares one lockfile, so one upgrade can break somebody else's feature.

03

Framework lock-in

Moving to a new framework means rewriting everything at once.

The idea

One shell, many independent micro-apps

  • Own deploy cycle for each micro-app
  • Own framework: React and Vue side by side
  • Own team: clear ownership boundaries
  • Loaded at runtime, never bundled together

What the shell owns

Routing, layout and auth state. Micro-apps plug in through a single exposed App entry and talk through typed events, never through direct imports.

Module Federation

Wiring is configuration, not code

// shell/vite.config.ts (host)
federation({
  name: 'shell',
  remotes: {
    mfe_react: process.env.REMOTE_REACT_URL
      ?? 'http://localhost:3001/…/remoteEntry.js',
    mfe_vue: process.env.REMOTE_VUE_URL
      ?? 'http://localhost:3002/…/remoteEntry.js',
  },
  shared: ['react', 'react-dom', 'vue', '@mfe/shared'],
})
// mfe-react/vite.config.ts (remote)
federation({
  name: 'mfe_react',
  filename: 'remoteEntry.js',
  exposes: {
    './App': './src/App',
  },
  shared: ['react', 'react-dom', '@mfe/shared'],
})

Every environment points at its own remotes through env vars. Shared dependencies are declared on both sides, so host and remotes reuse one copy instead of each bundling its own.

Runtime loading

A broken remote never takes the shell down

const ReactApp = lazy(() => import('mfe_react/App'))

<Route path="/react/*" element={
  <RemoteBoundary name="React app">
    <ReactApp />
  </RemoteBoundary>
} />

<Route path="/vue/*" element={
  <VueMounter factory={() =>
    import('mfe_vue/App')} />
} />
  • lazy + Suspense: remotes load only when their route is visited
  • RemoteBoundary: an error boundary shows "unavailable" instead of a blank page
  • VueMounter: mounts a Vue app inside React and unmounts it cleanly when you navigate away

Shared state

Auth lives in the shell, every app reads it

  • authStore: a tiny store with a subscribe method, no framework needed
  • The shell listens for user:login and user:logout and updates the store
  • One listener throwing an error doesn't stop the others: each call is isolated in try/catch

Security boundary

Any micro-app can emit user:login, so the store is UI state only. Never use it to authorize anything: roles must come from a token the server has verified.
